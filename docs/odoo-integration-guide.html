About secrets in this document

No real key, password or token appears here. Keys are written as placeholders such as pk_live_xxx and sk_live_xxx. The only real address used is the public brainBox server https://port.smartpowerbilling.com.

1Executive summary

Brainbox AI is an AI assistant that answers questions from a company's own knowledge (documents, FAQs, past support tickets). It has three parts, and Odoo is only one of the places where it can appear.

B

brainBox = the brain

Runs on your server (port.smartpowerbilling.com). Keeps each client company's knowledge separate, finds the relevant passages, has the AI model write the answer, and remembers the conversations.

S

SDKs = the faces

Ready-made chat windows: sdk-web (websites and Odoo), sdk-react (React / Next.js) and sdk-react-native (mobile apps). They show the chat; there is no AI inside them.

O

Odoo add-on = the bridge

brainbox_ai puts the web chat inside Odoo, adds a settings screen, and passes each message to brainBox with the company's secret key and the user's identity.

In plain words

brainBox is a call centre with one expert per client company; the SDKs are the telephones; the Odoo add-on is the receptionist inside Odoo. She checks who is calling, dials the right expert with the company's private access code and passes the answer back. She never answers questions herself and keeps no notes.

Five facts to remember

FactWhat it means
Odoo contains no AIAll AI work happens on the brainBox server.
Odoo stores no chatsConversations live on brainBox, per user; Odoo keeps only its settings.
The secret key never reaches browsersIt stays on the Odoo server; users' browsers only talk to Odoo.
Each company is sealed offEach company is a separate "tenant"; a key opens only its own tenant.
You control accessNobody can use your brainBox without a key you created, and you can revoke it.

What Odoo users see: a chat button in a corner of every Odoo screen (or a docked panel, or a sparkle icon in the top bar), an AI Assistant app with full-screen chat and past conversations, and optionally a chat box inside a specific form that tells the AI which record is open.

The one-sentence version for your boss

"Our AI runs on our own server and keeps every client company's knowledge in a sealed compartment; the Odoo add-on is just a secure doorway that shows our chat inside Odoo and passes questions to our server with that company's private key, so nobody can use it, or see another company's data, without a key we issued and can revoke at any time."

2The big picture

The same brainBox server serves every channel. What changes between channels is how the message reaches it and which key is used.

A. Inside Odoo (the brainbox_ai add-on)

B. On a plain HTML website (no Odoo)

In plain words

A website visitor is a stranger, so the website uses a front-door key that only lets people ask public questions. Odoo users are known, logged-in people, so Odoo can safely use the company's office key and tell brainBox who each user is.

For developers

Odoo runs the SDK with apiUrl: '/brainbox_ai/proxy' and no apiKey. Because the proxy is on the same origin, there is no CORS and the Odoo session cookie authenticates the user. A website can also put its own proxy in front of the SDK ("proxy mode") to get the same protection.

3A message's journey

Example: Ada works in customer service at a company called Acme. She is logged into Acme's Odoo and types in the chat: "When is my bill due?"

The same steps in words

  1. Ada asks. She types the question and presses Enter. The chat window shows "Thinking…".The SDK sends POST /brainbox_ai/proxy/api/chat to Odoo itself, with her Odoo login cookie and the header X-Brainbox-Proxy: 1. It contains no key and no tenant.
  2. Odoo checks the caller. Is the request coming from the Odoo screen, is Ada logged in, is she in an allowed group, is this a permitted kind of request, is the add-on configured? If any answer is no, Odoo refuses and the chat shows a friendly error.controllers/proxy.py: 403 without the header or for users outside "Allowed groups", 404 for paths not on the whitelist, 503 when not configured.
  3. Odoo writes the "envelope". It removes anything the browser claimed about identity and writes the truth: Ada's id, her name, her role, and Acme's secret key.Sets user_id = "odoo:<database>:<user id>", user_name, user_role (from the role mapping), tenant_id (if set) and Authorization: Bearer sk_live_xxx.
  4. Odoo forwards to brainBox at https://port.smartpowerbilling.com/api/chat and waits up to 200 seconds.
  5. brainBox identifies the company from the key. The key is looked up (only its fingerprint is stored), must be active and not expired. It belongs to tenant "acme", so everything that follows happens inside Acme's compartment. Because it is a secret key, brainBox trusts the role "internal" sent by Odoo.
  6. brainBox opens Ada's conversation. It is stamped with her user id, so no other user can open it. It also checks whether the same question was answered within the last hour for the same company and role (cache).
  7. brainBox searches Acme's knowledge for the 5 most relevant passages, but only among documents Ada's role may read (for "internal": public, customer, vendor and internal documents).
  8. The passages come back from the knowledge base (a PostgreSQL database with vector search).
  9. The AI model writes the answer from those passages, with instructions such as "say you don't know rather than guess" and "never reveal other customers' details".Ollama is called first; OpenAI is used as a fallback if configured.
  10. The answer comes back from the model.
  11. brainBox saves the question and the answer in Ada's conversation, and caches the answer for one hour.
  12. brainBox replies to Odoo with the answer and the conversation id.
  13. Odoo passes the reply back unchanged, and the widget displays it, formatted (lists, tables, links). The next time Ada opens the chat, her past conversations are listed.
In plain words

If a website visitor asked the same question through a public website, steps 2 and 3 would not exist, the publishable key would make brainBox treat them as "public", and step 7 would search only public documents. Same brain, different access.

4Companies (tenants) and keys

brainBox is shared by many companies. Two ideas keep them apart: tenants (separate compartments) and keys (who may enter which compartment, and with how much power).

Tenant: one company's separate brain

A tenant is one customer company on your brainBox server, identified by a short id such as acme. Everything brainBox stores is labelled with a tenant: the knowledge (documents, FAQs, tickets), the conversations, the cached answers, the keys. A search for Acme only looks at Acme's documents; a cached answer for Acme is never served to Globex.

Three kinds of keys

Publishable · pk_live_…

The front-door key

For public places: websites, mobile apps. Anyone may see it. It opens one company's front desk and lets visitors ask questions as "public", nothing more.

Secret · sk_live_…

The office key

For servers only (Odoo, a company back-end). Opens one company's whole office: chat with trusted roles, and teach / manage the company's knowledge. Must never appear in a web page.

Admin token

The master key

Held only by you, the brainBox operator. It doesn't chat; it creates, lists and revokes keys for every company. Stored in the brainBox server's settings file.

What it can dopk_ publishablesk_ secretAdmin token

List / read conversationsyesyesno
Attach files / images to a chatyesyesno
Assert a user role (internal, admin…)no, ignoredyesno
Teach the AI (train, ingest, delete sources)no (403)yesno

Scopeone tenantone tenantwhole server
Where it is keptweb page / app codeOdoo Settings (server side) or another server's configbrainBox server .env (BRAINBOX_ADMIN_TOKEN)

The basic health check (GET /api/health) needs no key at all; it only says "the server is running".

Important: the tenant comes from the key

A key belongs to exactly one tenant. If a request also names a tenant and it is a different one, brainBox refuses it (403 "tenant_id does not match API key"). In Odoo you may therefore leave Tenant ID empty when a secret key is set; if you fill it in, it must be exactly the key's tenant.

How keys are stored and created

  • brainBox stores only a fingerprint (SHA-256 hash) of each key, plus its type, tenant, a name, a short visible prefix (e.g. sk_live_Ab3x) for recognising it, active/revoked status, optional expiry date and "last used" time.
  • The full key is shown only once, at creation. If it is lost, create a new one and revoke the old one.
  • An existing key can be imported (so already-deployed sites keep working); it must be at least 24 characters long.

Option 1: command line on the brainBox server (works without the admin token)

# create a secret key for Acme's Odoo server (prints the key once)
python -m app.cli keys create --tenant acme --type secret --name "Acme Odoo server"
# create a publishable key for Acme's public website, expiring 1 Jan 2027
python -m app.cli keys create --tenant acme --type publishable --name "Acme website" --expires 2027-01-01
# list keys (never prints full keys), optionally for one tenant
python -m app.cli keys list --tenant acme
# revoke key number 42 immediately
python -m app.cli keys revoke 42
# with Docker, run the same commands inside the API container
docker exec -i brainbox-api python -m app.cli keys list

Option 2: the admin API (requires the admin token)

POST   https://port.smartpowerbilling.com/api/admin/keys      { "tenant_id": "acme", "key_type": "secret", "name": "Acme Odoo" }
GET    https://port.smartpowerbilling.com/api/admin/keys?tenant_id=acme
DELETE https://port.smartpowerbilling.com/api/admin/keys/42
Header on every call:  X-Admin-Token: <your admin token>

Without BRAINBOX_ADMIN_TOKEN set on the server, the admin API answers 503 (disabled); with a wrong token, 401. A staff dashboard for managing keys and knowledge is coming (being built now); this document covers the current mechanisms only.

What happens if a key leaks?

KeyWhat someone could do with itWhat to do
pk_ publishableNothing secret: ask questions as "public" (public knowledge only) and use your AI capacity. It can also list conversations that are not tied to a specific user. A pk_ is public by design, so "leaking" is expected.If abused, revoke it (keys revoke <id>), create a new one, update the website.
sk_ secretSerious. Read all of that company's knowledge (by claiming the "admin" role), read its users' conversations, add or delete its training data. Other companies are not affected.Revoke immediately, create a new secret key, paste it into Odoo Settings (Secret API key), save.
Admin tokenCritical. Create keys for any company, and so reach any company's data.Change BRAINBOX_ADMIN_TOKEN in the server .env, restart brainBox, review keys list and revoke unknown keys.
For developers: enforcement switch

Keys are enforced when REQUIRE_API_KEY=true (the default). Setting it to false is a temporary migration mode in which no key is checked and the tenant and role are taken from the request; brainBox logs a warning at start-up. It should stay true in production. Keys are read from X-API-Key or Authorization: Bearer (app/dependencies.py).

5Who sees what: roles and audiences

Inside one company, not everyone should see everything. brainBox uses two labels: every piece of knowledge has an audience, and every question has a role. A role can only read certain audiences.

Audience: who a document is for

AudienceMeant for
publicanyone, including anonymous website visitors
customerlogged-in customers
vendorsuppliers / vendors
internalstaff (default for new training sources)
adminadministrators only

Role: what a person may read

RoleReads audiences
admineverything
internalpublic, customer, vendor, internal
customer (= portal)public, customer
vendorpublic, vendor
publicpublic only

How Odoo decides a user's role

The add-on looks at the user's Odoo groups and applies the first rule that matches (Settings › Brainbox AI › Roles):

#Odoo userRole sentSo they can read
1Administrator (Settings rights)admineverything
2Member of a "Vendor group"vendorpublic + vendor
3Member of a "Customer group"customerpublic + customer
4Other internal (employee) user"Role of internal users": internal (default) or publicpublic, customer, vendor, internal (or public only)
5Portal user"Role of portal users": customer (default), portal, vendor or publicdepends on the choice
6Anyone elsepublicpublic only

Vendor and customer groups are chosen by the Odoo administrator (any Odoo groups). Unknown or missing roles are always treated as public by brainBox: the safe default.

Why the browser cannot fake its role

  1. Odoo overwrites identity. The proxy deletes any tenant_id, user_id, user_name or user_role sent by the browser and writes the real values from the Odoo login.
  2. Only secret keys may state a role. With a publishable key, brainBox ignores the role and uses public, so a website visitor who edits the page code still gets public answers only.
  3. Filtering happens before the AI sees anything. Documents the role may not read are never retrieved, so the AI cannot leak them, even by accident.
  4. Cached answers are kept per company and per role, so a "public" user can never receive an answer that was built for "internal".
  5. Conversations belong to one user. Each Odoo user's conversations are stamped with odoo:<database>:<user id>; another user asking for them gets "Session not found".
Important: the add-on lives in Odoo's back-office

The widget is loaded in Odoo's back-office screens (the web.assets_backend bundle) and the AI Assistant menu is for internal users. Portal customers using the Odoo website/portal pages do not see it today, so the "portal" and "customer group" settings matter only for users you deliberately give back-office access. Who may use it at all is controlled by Allowed groups (empty = all internal users; administrators always).

For developers

Role mapping: brainbox.ai.backend._user_role(). Audience filtering: app/permissions.py (allowed_audiences) applied in the search step log_node. Documents created before audiences existed are treated as LEGACY_DOC_AUDIENCE (default public). The audience of a training source can be changed later with PATCH /api/train/sources/{id}; this relabels all its documents and clears the company's cached answers.

6If another company installs the add-on: does it talk to my brainBox?

Short answer

Only if you let it. The add-on ships with no server address and no key (the Backend URL default is empty). A freshly installed copy talks to nobody. It reaches your brainBox only when the company's administrator enters your server's URL and a key that you created for their tenant. Without a valid key, your server refuses every chat request (401).

The rules, in plain words

  • The URL decides which server. The Odoo administrator types the Backend URL. If they type yours, requests go to your server; if they run their own brainBox, they type that one instead and you are not involved.
  • The key decides which company. On your server, the key alone decides the tenant. You create one tenant per customer company and give that company only its own keys.
  • Their data stays in their tenant. Their knowledge, conversations and cached answers are labelled with their tenant and never mixed with other companies'.
  • You stay in control. You can see every key (keys list: tenant, name, last used) and revoke any key at any time; the add-on then stops working for that company immediately, and their Odoo shows a "cannot get an answer" error banner instead of answers.
  • Several Odoo databases, one tenant. A company with several Odoo databases can use the same tenant; users stay separate because their id includes the database name (odoo:<database>:<user id>).

Onboarding checklist for a new customer company

  • Choose the tenant id (short, lowercase, e.g. globex).
  • Create a secret key on your server: python -m app.cli keys create --tenant globex --type secret --name "Globex Odoo". Copy the key shown once.
  • Send the key securely (password manager or a one-time secret link, not plain email or chat) together with the Backend URL https://port.smartpowerbilling.com.
  • Load their knowledge into their tenant with the training tools (secret key), and label each source with the right audience (public / customer / vendor / internal / admin).
  • They install the add-on in Odoo (Apps › Update Apps List › Brainbox AI › Activate).
  • They configure Settings › Brainbox AI: Backend URL, Secret API key; leave Tenant ID empty (or set exactly globex); choose display mode, allowed groups, role mapping and branding.
  • Test connection, then ask a real question in the chat to confirm the key works (see the note below).
  • Optional website: create a publishable key (--type publishable) for their public site and give them the sdk-web snippet (section 9).
  • Record it: note the key ids, names and expiry dates so you can revoke or rotate them later.
Note about "Test connection"

The Test connection button calls /api/health, which brainBox answers without checking keys. A green result proves the server is reachable, not that the key is right. A wrong key or tenant only shows up when the first real question is sent (the chat displays an error banner).

7Installation and configuration

Install

  1. Put the folder in place. Copy brainbox_ai into an add-ons folder listed in addons_path of odoo.conf (here: odoo\custom_addons).Depends on Odoo modules base, web, base_setup and the Python package requests (shipped with Odoo).
  2. Install it. In Odoo: Apps › Update Apps List, search "Brainbox AI", click Activate. Or from the command line (below).
  3. Configure it. Settings › Brainbox AI (also AI Assistant › Configuration). Only administrators see these settings.

Running Odoo (from C:\Users\USER\Documents\PERSONAL\odoo)

# start the server  →  http://localhost:8069
.venv\Scripts\python.exe odoo-bin -c odoo.conf
# install the add-on in database <db> (one-shot)
.venv\Scripts\python.exe odoo-bin -c odoo.conf -d <db> -i brainbox_ai --stop-after-init
# upgrade it after changing its files
.venv\Scripts\python.exe odoo-bin -c odoo.conf -d <db> -u brainbox_ai --stop-after-init

If a server already runs on port 8069, add --http-port 8075 (or another free port) to the one-shot commands. After an upgrade, restart the running server (or open Odoo with ?debug=assets) so browsers get the new files. Upgrading from version 1.x deletes the old brainbox_ai_session table (see the migration script); conversations are on brainBox and are not affected.

The AI Assistant app

A new app in the Odoo home menu, AI Assistant (internal users), with two menus: Chat (a full-screen chat with the conversation list: New chat, search, conversations grouped by Today / Yesterday / This week / Older) and Configuration (administrators only, opens the settings). While this app is open, the floating button or sidebar is hidden and comes back when you leave.

Embedding the chat in a specific form

A developer can place the chat inside any Odoo view with one line, <widget name="brainbox_chat"/>. By default the record being viewed is sent along with each question (e.g. "Odoo record: Contact — Acme Corporation (id 10)"), and each record keeps its own conversation. Example, adding it to the contact form, in your own module that depends on brainbox_ai:

<record id="view_partner_form_brainbox" model="ir.ui.view">
    <field name="name">res.partner.form.brainbox</field>
    <field name="model">res.partner</field>
    <field name="inherit_id" ref="base.view_partner_form"/>
    <field name="arch" type="xml">
        <xpath expr="//sheet" position="inside">
            <widget name="brainbox_chat" height="520" title="Ask about this contact"/>
        </xpath>
    </field>
</record>
AttributeDefaultMeaning
height520Height in pixels (minimum 240).
titleHeader title from SettingsTitle shown in the chat header.
record_context1 (on)0 sends questions without the record description.

The view can also be created without code from Settings › Technical › Views in developer mode.

Updating the bundled widget (SDK)

The add-on contains an unmodified copy of the official web SDK. Never edit it inside Odoo: change the SDK project, then copy it in with the helper script, and upgrade the module (-u brainbox_ai) or restart Odoo.

# from the add-on folder: copy from the local SDK project
.\tools\sync_sdk.ps1 -SdkPath C:\Users\USER\Documents\PERSONAL\ai\sdk-web
# or download version 2.x of the npm package "spres-web" from the jsDelivr CDN
.\tools\sync_sdk.ps1 -Version 2

Alternative: keep the bundled copy and set SDK script URL to load the widget from a CDN or your server.

About "models" (database)

In plain words

The add-on creates no tables for chats or messages. Its settings are saved as Odoo system parameters (one line per setting, all named brainbox_ai.…).

ModelWhat it is
brainbox.ai.backendAbstractModel: a helper with code only, no database table. Reads settings, decides who may use the assistant and with which role, builds the browser configuration, runs the health check.
res.config.settings (extended)Odoo's standard settings screen, extended with the Brainbox AI fields. It is a temporary (transient) model: values are copied into system parameters on Save, and Odoo regularly cleans up the screen's temporary rows.

Standard Python loaders: import the controllers (main, proxy) and the models (brainbox_backend, res_config_settings). No logic.

controllers/main.pynon-secret settings & logo for the browser

Gives the browser what it needs to draw the chat, and nothing secret.

  • /brainbox_ai/config (JSON-RPC, logged-in users): returns get_public_config(): allowed?, configured?, display mode, colours, names, logo URL, welcome messages, quick actions, position, SDK script URL. Never the key.
  • /brainbox_ai/logo (GET, logged-in users): serves the uploaded logo, detecting PNG / JPEG / GIF / WebP / SVG, with a strict Content-Security-Policy and nosniff (an SVG cannot run scripts) and 7-day private caching.
controllers/proxy.pythe messenger between browser and brainBox

Receives the widget's requests on Odoo's own address and forwards the allowed ones to brainBox, adding the secret key and the real user identity. It contains no AI logic and returns brainBox's answer unchanged.

  • Route /brainbox_ai/proxy/<path>, GET/POST, logged-in users only (auth='user'), csrf=False but requires the header X-Brainbox-Proxy: 1 (a cross-site form cannot send a custom header, so this blocks cross-site request forgery).
  • Refuses users outside Allowed groups (403), unknown paths (404), wrong methods (405), unconfigured module (503).
  • Removes tenant_id, user_id, user_name, user_role from the browser's data (JSON body, query or upload form) and sets the true values; adds Authorization: Bearer <secret key>.
  • Limits: JSON body 512 KB, uploads 10 MB, conversation ids checked against a safe pattern.
  • Errors: 504 if brainBox is too slow, 502 if unreachable or if the answer is not JSON (friendly message, details only in the Odoo log).

The add-on's "rule book": reads settings, decides access and roles, and checks the server.

  • Constants: display modes, positions, role choices and default values (e.g. colour #b93fff, bot name "Brainbox AI", empty Backend URL).

9The web SDK (sdk-web)

sdk-web is one JavaScript file with no dependencies. Any website can show the Brainbox chat by adding two small pieces of code. Odoo uses the very same file.

The plain-HTML snippet

<script src="https://port.smartpowerbilling.com/sdk/brainbox-web-sdk.js"></script>
<!-- or from the CDN: https://cdn.jsdelivr.net/npm/spres-web@2 -->
<script>
  const bb = Brainbox.init({
    apiUrl: 'https://port.smartpowerbilling.com',   // the brainBox server
    apiKey: 'pk_live_xxx',                          // a PUBLISHABLE key only
    mode: 'floating', position: 'bottom-right',
    theme: { primary: '#2563EB' },
    branding: { botName: 'Acme Assistant', subtitle: 'Ask us anything' },
    launcher: { text: 'Support chat' },
    quickActions: ['Opening hours?', 'How do I pay my bill?']
  });
</script>

For developers: proxy mode on any site

A website with logged-in users should copy Odoo's approach: a small endpoint on its own domain that checks the session, adds Authorization: Bearer sk_live_xxx, the tenant and the user, and forwards to brainBox; then Brainbox.init({ apiUrl: '/your/proxy', credentials: 'same-origin' }) without a key. When tenantId and user.id are not set, the SDK does not send them, so the proxy decides.

10Security and known limitations

What is protected, and how

RiskProtection
Secret key stolen from a browserThe key is stored only on the Odoo server, never included in the settings sent to the browser, never shown again in the form, and only administrators can change it.
One company reading another's dataThe tenant comes from the key; a different tenant in the request is refused (403). Searches, conversations and cached answers are all limited to that tenant.
A user pretending to be someone else or claiming a higher roleThe Odoo proxy overwrites user id, name, role and tenant with the real logged-in values. Publishable keys are always "public" on brainBox.
Restricted knowledge leaking through the AIDocuments are filtered by audience before the AI sees them; the cache is separated by role; the AI is told not to reveal other customers' details.
Reading another user's conversationsConversations are stamped with the user id; other users get "Session not found" (existence is not revealed).
Misuse of Odoo as an open relayOnly logged-in users in Allowed groups; only 7 chat endpoints are forwarded; training, ingestion and key management are blocked (404).
Cross-site request forgeryThe proxy requires the custom header X-Brainbox-Proxy: 1, which another website cannot send to Odoo.
Oversized or malicious uploads10 MB limit (Odoo and brainBox), JSON limited to 512 KB, conversation ids validated; brainBox accepts only JPEG/PNG/GIF/WebP as images and strips paths from file names.
Malicious content in answers or logoThe SDK renders answers with a safe formatter (no raw HTML; only http/https/mailto links). The logo is served with a strict Content-Security-Policy.
Stolen key databasebrainBox stores only SHA-256 fingerprints of keys; keys can expire and be revoked; the admin token is compared in constant time.

Known limitations (as of this version)

LimitationDetails
No streamingThe answer arrives all at once; the widget shows "Thinking…" meanwhile. A slow answer can take up to ~3 minutes (the Odoo proxy waits 200 s, then shows a timeout message).
Uploads are stored, not learned fromFiles and images attached in the chat are saved on the brainBox server (in a temporary folder) and noted in the conversation, but the AI does not read them when answering and they are not added to the knowledge base. Teaching the AI is done through the training tools with a secret key.
Answer cache keyed on the first 50 charactersAnswers are cached for 1 hour per tenant and role using only the first 50 characters of the question. Two different questions that start with the same 50 characters can receive the same answer. This especially affects the embedded form widget, because each question there starts with the same "Context: Odoo record: …" line for a given record. Worth fixing in brainBox (e.g. hash the whole question).
Test connection does not check the key/api/health is public, so a successful test proves only that the server is reachable. A wrong key or a mismatching Tenant ID appears at the first real question (401 / 403).
Back-office onlyThe add-on adds the chat to Odoo's back-office, not to the Odoo website or customer portal pages.
Publishable keys are open by naturebrainBox accepts requests from any website (CORS open) and has no per-key website allow-list or rate limiting yet (listed as next steps). A copied pk_ key can be used elsewhere, but only for public answers. A pk_ key can also list conversations that are not tied to a user.
History depends on brainBoxAll conversations live on brainBox. If it is down, Odoo shows an error banner with Retry. Per-user history is tied to odoo:<database>:<user id>; renaming the Odoo database gives users a fresh history.
Per-browser preferencesThe open/closed state, docked/floating choice and last conversation are remembered per browser, not per Odoo user account.
Staff dashboardA web dashboard for staff (keys, knowledge, conversations) is being built and is not covered here; today keys are managed with the CLI or the admin API.

11Glossary

TermMeaning in plain words
brainBoxYour AI server application. It stores each company's knowledge, searches it, asks an AI model to write answers and keeps the conversations.
TenantOne customer company on brainBox: a sealed compartment with its own knowledge, conversations and keys.
SDK"Software development kit": a ready-made building block that developers drop into their software. Here: the chat window (sdk-web, sdk-react, sdk-react-native).
Add-on / moduleA package that extends Odoo. brainbox_ai is the Odoo add-on for Brainbox.
ProxyA middleman that receives a request and passes it on. Odoo's proxy passes chat requests to brainBox, adding the secret key and the user's identity.
APIThe set of addresses (such as /api/chat) through which programs talk to brainBox.
API keyA long password that identifies a client program and its tenant. Publishable (pk_): safe in public pages, public answers only. Secret (sk_): servers only, full access to one tenant.
Admin tokenThe operator's master password on the brainBox server, used only to create, list and revoke keys.
RoleWho is asking (admin, internal, customer, vendor, public). It decides which knowledge may be used to answer.
AudienceLabel on each piece of knowledge saying who it is for (public, customer, vendor, internal, admin).
Session / conversationOne chat thread with its messages, stored on brainBox, owned by one user.
Knowledge baseThe company's documents, FAQs, tickets and records that brainBox has learned, cut into passages.
Embedding / vector searchEach passage is turned into a list of numbers that captures its meaning; the question is turned into one too, and the closest passages are found ("semantic search"). Stored in PostgreSQL with pgvector.
AI model (LLM)The language model that writes the answer from the passages found. brainBox uses Ollama, with OpenAI as a fallback.
Training / ingestionAdding knowledge to a tenant (files, text, external APIs such as a helpdesk). Requires a secret key; not possible through Odoo's proxy.
CacheA short-term memory of recent answers (1 hour, per tenant and role) so repeated questions are answered instantly.
System parameterOdoo's key-value settings store (ir.config_parameter), where the add-on saves its settings.
AbstractModelAn Odoo model that holds code but no database table.
SystrayThe row of small icons at the top right of Odoo.
CORS / CSRFBrowser security rules about which websites may call which servers, and a type of attack where another site tricks a browser into sending requests. The proxy design avoids both problems.
