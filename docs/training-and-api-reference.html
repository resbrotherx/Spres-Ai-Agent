1How Brainbox learns

Brainbox does not "study" your documents the way a person does, and it does not change the AI model. It builds a searchable library of short passages from your content and, for every question, hands the AI the few passages that fit best. The AI then writes the answer from them.

The five training steps in plain words

  1. Upload. You give Brainbox content: a file, a piece of text you type, or the address of a system (for example your support desk) that it can read from.Each upload becomes one training source that you can see in the list, rename, relabel, re-sync or delete.
  2. Read the text. Brainbox pulls the plain text out of the file. Pictures are ignored, and a scanned PDF (a photo of paper) has no text, so it can't be read.PDF via pypdf, Word via python-docx, XML via defusedxml; text files are decoded as UTF-8 (with fallbacks).
  3. Split into chunks. Long text is cut into passages of about 1,000 characters (roughly half a page). Neighbouring chunks overlap by about 150 characters so a sentence cut in two is never lost. Each support ticket becomes its own chunk.Each chunk starts with a label such as [Manual.pdf - Page 4] so the AI knows where it came from.
  4. Fingerprint (embedding). Each chunk is turned into a list of 768 numbers that describe what it means. Passages about the same topic get similar numbers even when they use different words ("bill" and "invoice").Model: BAAI/bge-base-en-v1.5 (setting EMBEDDING_MODEL), stored in PostgreSQL with pgvector.
  5. Store per company. Chunks are saved in the company's own space (its tenant) together with an audience label that says who may see them (section 4).The same text in two companies is stored twice and never mixed. The same text uploaded twice in one source is stored once.

And when someone asks a question

The question gets a fingerprint too. Brainbox looks up the 5 chunks whose fingerprints are closest, but only inside the asker's company and only among chunks whose audience the asker's role may see. The AI model receives those 5 chunks plus the question and is told to answer only from them. If it can't, it says so ("I don't have that information yet…"), and your staff get an alert so they can teach it (section 5).

In plain words

Think of a librarian with an index card for every half page of your documents. When a question comes in, she pulls the five cards that match it best (skipping cards stamped "staff only" if the asker is a customer) and hands them to a writer who drafts the reply. Training adds cards; deleting a source pulls its cards out of the drawer.

For developers
  • Similarity is cosine distance (0 = same meaning, larger = less related). The closest distance is also used to detect weak answers (default threshold 0.55).
  • Answers are cached for 1 hour per company + role + question. The cache is cleared whenever a training job finishes and when a source is relabelled or deleted, so new knowledge shows up straight away.
  • The AI model is Ollama (OLLAMA_MODEL); OpenAI is used as a fallback only when USE_OPENAI=true and a key is set.

2Ways to train

There are three ways to add knowledge. They all end up in the same library and follow the same audience rules.

1

The dashboard (no code)

The Training page of the staff dashboard (the TrainingPanel) has three tabs: Upload files, Connect API and Paste text, plus a searchable list of every source with its status, audience, chunk and record counts, and Sync / Delete buttons.

2

The API (automation)

A developer can call the same endpoints from a server with a secret key: /api/train/file, /api/train/text and /api/train/api-source. Useful to push new manuals or FAQs automatically, or to sync a support desk every night.

3

Answering gaps

When Brainbox couldn't answer a question, it appears in the Knowledge gaps inbox. A trainer types the right answer and clicks Answer & train: the answer becomes a new training source and the gap is closed.

Using the Training page step by step

  1. Sign in to the staff dashboard with your email and password. You need the trainer role or higher to add or change knowledge; viewers can only look.
  2. Pick a tab. Upload files: drag one or more files in (PDF, XML, TXT, MD, CSV, JSON, DOCX, up to 25 MB each). Paste text: give it a name and paste the text. Connect API: enter the address of your support system (section 3).
  3. Choose the audience ("Audience · who can see this"). The default is Internal staff. Choose Public only for content you would happily publish on your website.
  4. Send it. The source appears in the list as queued, then processing, then completed or failed. The list refreshes by itself every few seconds while something is processing.
  5. Check the result. A completed source shows how many chunks (and, for tickets, records) it produced. A note such as "3 of 40 pages had no extractable text" means part of the file was skipped; "failed" always comes with a reason.

3Connecting a customer-support system

Past support tickets are the most valuable training data: each one is a real customer question together with the answer your team gave. Brainbox can read them straight from your helpdesk's API (Zendesk, Freshdesk, your own system…) and turn every ticket into "customer issue + our response".

What your API should return

Any JSON response that contains a list of tickets works. The list can be the whole response, or sit under a key such as data, results, items, tickets, records, conversations, issues or cases (two levels deep at most, for example data.tickets). If it is somewhere else, set data path to its location, for example response.payload.rows.

Each ticket should contain a customer's issue and your answer, either as two fields or as a conversation (a list of messages). Brainbox recognises the usual field names on its own:

MeaningField names recognised automatically (first match wins)
Ticket idticket_id, ticket_number, ticket_no, case_number, case_id, id, number, key, reference, ref, uuid
Titlesubject, title, summary, topic, headline, issue_title, name
Customer issuecustomer_issue, issue, question, problem, description, issue_description, customer_message, complaint, query, inquiry, enquiry, request, body, message, content, details, text, comment
Our responseour_response, response, answer, reply, resolution, solution, agent_response, agent_reply, support_response, resolution_notes, resolution_note, response_text, answer_text, reply_text, resolution_text, final_response, workaround, fix
Conversationmessages, comments, replies, conversation, conversations, thread, threads, interactions, conversation_parts, posts, notes (must be a list)
Extra detailsstatus, priority, category, type, tags, product are added at the end of the chunk when present (short values only).

Matching ignores case, spaces, dashes and underscores: Customer Issue, customer_issue and customerIssue are the same. Fields one level down are found too (for example Jira's fields.summary). HTML in any field is turned into plain text.

Mapping fields yourself

When the names are unusual, fill in the mapping. Every value is a "dot path" inside one ticket: fields.summary, requester.message, items.0.body.

MappingUse it for
id_fieldThe ticket number. Strongly recommended: re-syncs use it to replace a ticket that changed.
title_fieldThe subject line, shown in the chunk header.
question_fieldThe customer's issue.
answer_fieldYour team's response or resolution.
messages_fieldThe list of messages in the conversation.
extra_fieldsA list of other fields to add (replaces the default status / priority / category / type / tags / product).

Conversation threads

For each message Brainbox finds the text (body, text, message, content, html_body…) and decides whether the customer or an agent wrote it, in this order:

  1. yes/no flags such as is_agent, is_staff, is_admin, is_customer, incoming, private: true;
  2. a role-like field (role, author_type, sender_type, from, direction, source…) or an author / user object whose value contains words like agent, admin, staff, support, team, bot, outbound (agent) or customer, user, client, requester, contact, inbound (customer);
  3. otherwise: the first message is the customer, later messages by the same author id are the customer and anyone else is an agent; failing that, turns simply alternate.

If the first message only repeats the issue, it is left out so the chunk doesn't say it twice.

Test connection first

Test connection fetches the first page only, trains nothing and shows: whether it worked, the HTTP status, how many records it found, where it found them (data_path), the field names of the first record, how many records it had to skip, and a preview of the first 5 chunks exactly as they will be stored. Fix the mapping until the preview reads well, then click Save & train.

In plain words

If the preview says "Records were found but none had a recognizable issue/response", Brainbox found your tickets but couldn't tell which field is the question and which is the answer: set question field and answer field. If it says "No records found", set the data path to where the list of tickets is.

Re-sync: keeping it up to date

Click Sync on the source (or call POST /api/train/sources/{id}/sync) to fetch everything again. Nothing syncs automatically: if you want a nightly sync, have a server call that endpoint on a schedule.

What happened to a ticketWhat a sync does
UnchangedSkipped: same text, nothing is re-processed.
Changed (new reply, edited text)The new version is stored and the old version of that ticket id is removed. Without an id, the old version stays next to the new one.
NewAdded.
No longer returned by the APIKept. A sync never deletes tickets it didn't see (the API may simply return the latest 10 pages). To start clean, delete the source and add it again.
Important
  • Only one sync per source at a time: a second sync gets "This source is already syncing" (unless the first has been stuck for more than 30 minutes).
  • The address, headers and mapping of a saved source can't be edited (only its name and audience). To change them, delete the source and connect again.
  • Headers and query values whose name looks secret (containing auth, token, key, secret, password, cookie, session, signature, credential or bearer) are hidden as •••• when sources are listed, but they are stored on the brainBox server so it can sync. Use a read-only helpdesk token.
  • Choose the audience carefully: tickets usually contain customer details. The AI is instructed never to reveal other customers' names or contact details, but internal is the safe default.
For developers

source_type: "api_generic" treats records as generic data instead of tickets: each becomes Record #id: title followed by every field as path: value lines. POST requests are supported (method: "POST" with a JSON body). Responses must be JSON; redirects are followed.

  • Files, pasted text and connected APIs default to internal when no audience is chosen.
  • Gap answers ("Answer & train") default to public, because they usually answer a customer's question. Change the picker before saving if the answer is internal.
  • Old content trained before audiences existed, and anything sent through the low-level /api/ingest endpoint without an audience, has no label.   • Audiences protect answers, not the training list: anyone with a secret key or a staff login can list every source of the company. And they only work if the role is right: a server that sends every user as admin shows everything to everyone.

How to relabel a source

In the Training list, click the source's audience pill and pick another audience (trainer role or higher). Through the API: PATCH /api/train/sources/{id} with {"audience": "customer"}. Every chunk of the source is relabelled at once and cached answers are cleared, so the change applies to the very next question.

5Knowledge gaps and staff alerts

Brainbox notices when it could not answer properly, writes the question down in a Knowledge gaps inbox and tells your staff. Answering a gap teaches Brainbox, so the same question is answered next time. This is the fastest way to improve it.

When a question is recorded as unanswered

After every answer Brainbox checks, in this order, whether it was weak. The first matching reason is recorded:

ReasonShown asWhat it means
llm_unavailablethe AI model was unavailableThe AI model didn't respond, so a fallback message was sent. Usually a server problem, not missing knowledge.
no_contextno matching knowledgeNothing in the library that this person may see matched at all.
llm_unknownthe assistant didn't knowThe answer says it doesn't know. The AI is told to start such answers with "I don't have that information yet"; similar phrases ("I couldn't find…", "not in the knowledge base") are detected too.
low_confidencelow-confidence matchSomething was found, but even the closest chunk was far from the question: its distance was above the company's gap threshold (default 0.55; 0 = identical meaning, 2 = opposite).
negative_feedbacknegative feedbackA user gave the answer a thumbs-down (optionally with a comment).

Admins can change the gap threshold per company in Settings (any number from 0 to 2). Lower it to flag more answers as weak, raise it to flag fewer. A cached answer that was weak the first time still counts as unanswered when it is served again.

Grouping

Questions are grouped per company by their normalized text: lower-case, punctuation removed, spaces collapsed. "How do I reset my PIN?" and "how do i reset my pin" are one gap. A repeat increases its occurrences counter and updates "last seen", the asker and the answer given; the status stays as it was, except that a thumbs-down re-opens a resolved gap. Gaps are sorted by when they were last asked, so the most current problems come first.

  • Emails need the server's email (SMTP) to be configured. Without it, only in-app notifications are created.
  • To avoid floods, each company sends at most 20 alert emails per hour by default (Settings → Gaps & alerts, 0 to 1000; 0 turns alert emails off). Beyond that, emails are skipped but in-app notifications are still created. Invitations and password resets are never limited.

Answering a gap ("Answer & train")

  1. Open the gap from the bell or the Gaps inbox. You see the question, the reason, how often it was asked, by whom (name and role, when the website or Odoo sent them), the answer Brainbox gave and any feedback comment.
  2. Write the correct answer in your own words, as you would to a customer.
  3. Choose the audience ("Who can see this answer", default public) and decide on Also resolve similar open questions (ticked by default in the dashboard; off by default in the API).
  4. Click Answer & train. Brainbox creates a text training source named Answer: <first 60 characters of the question> containing Question: … and Answer: …, trains it, and marks the gap resolved with your name.

"Also resolve similar open questions" closes the other open gaps whose questions share at least 60% of their meaningful words with this one (common words like "how", "the", "my" are ignored) and links them to the same answer.

A trainer can also Dismiss a gap (spam, out of scope), Reopen it, or mark it resolved with a note (for example after uploading a better manual).

Thumbs-down feedback

Any chat window can send a rating for an answer with POST /api/chat/feedback (a publishable key is enough): up or down, with an optional comment of up to 2,000 characters. A thumbs-down creates or bumps a negative_feedback gap for the question and alerts staff. Changing your mind and rating the same answer again updates the rating; a second "down" on the same answer does not alert again.

Important

The ready-made chat widgets (sdk-web and the React ChatWidget / ChatPanel) don't show thumbs buttons yet. Feedback works today through the API (see the recipe in section 11), and staff can read the ratings in the Conversations view.

Inviting staff

  1. Staff → Invite. An admin or owner enters the email, an optional name and the role.
  2. The invitation is emailed with a link valid for 7 days. If the server can't send email, the dashboard shows the link to copy and send yourself. "Resend invite" makes a new link.
  3. The colleague opens the link, chooses a password (at least 8 characters) and is signed in. Admins get a "joined" notification.
  • One email address is one account, in one company. Inviting an address already used anywhere is refused.
  • Forgotten password: "Forgot password" emails a reset link valid for 1 hour (at most one email every 2 minutes). The answer is always "ok", so nobody can test which emails exist.
  • A sign-in lasts 12 hours. After 10 wrong passwords in 15 minutes for the same email and computer, sign-in is blocked for a while ("Too many failed attempts").
  • Deactivating or removing someone, or changing their role, takes effect on their very next click.

The very first owner

A new company has nobody to send the first invitation, so the server administrator creates the first owner, either on the server:

python -m app.cli staff create --tenant acme --email owner@acme.com --role owner --name "Ada Lovelace"
# prints an invite link (valid 7 days). Add --password to type a password instead.

or over HTTP with the admin token (POST /api/admin/staff, section 10). From then on, the owner invites everybody else from the dashboard.

For developers

Invite and reset links point to DASHBOARD_URL/#/accept-invite?token=… and …/#/reset-password?token=…. When DASHBOARD_URL isn't set, the browser's Origin header is used; emails are only sent when an absolute link can be built.

7Keys explained

Four kinds of credentials open brainBox. Each one says who is calling and which company they act for. Choosing the right one is the most important security decision when you connect Brainbox to something.

Publishable key · pk_live_…

For websites and apps

Safe to put in a web page or mobile app. It can only chat: ask questions, keep conversations, attach files to a chat, send feedback and read the widget's look. Every user is treated as public, so only public knowledge is used.

Secret key · sk_live_…

For servers only

Can do everything for its company: chat with a trusted role, train, list and delete sources, read task status. Never put it in a browser, a mobile app, a public repository or an email.

Staff login · <staff-jwt>

For people in the dashboard

What you get when you sign in with email and password. Works like a secret key for training (trainer role or higher to change things) and also opens the staff-only features: gaps, reports, staff, settings, keys. Expires after 12 hours.

Admin token · <admin-token>

For the server administrator

One long password set on the brainBox server (BRAINBOX_ADMIN_TOKEN). It manages keys for every company and can create a company's first owner. It can't chat or train.

Getting and managing keys

  • Dashboard: Settings → API keys (admin or owner). Give the key a name ("Website widget", "Odoo server"), pick publishable or secret, and optionally an expiry date. The key is shown once: copy it immediately. Revoke it there when it is no longer needed or may have leaked.
  • Server: python -m app.cli keys create --tenant acme --type secret --name "Odoo server", keys list, keys revoke 42.
  • brainBox stores only a fingerprint (hash) of each key, so a lost key can't be recovered: create a new one and revoke the old.
  • Expired and revoked keys get 401 Invalid or missing API key immediately.
Never put a secret key in a browser

Anything in a web page can be read by every visitor (View Source takes two seconds). A leaked secret key lets a stranger read your whole training list, delete it, or train Brainbox with false answers. If a website needs more than public answers, its own server must call brainBox with the secret key (a "proxy"), after checking who the user is. This is exactly what the Odoo add-on does.

In plain words

The publishable key is the shop's front-door bell: anyone can ring it and talk to reception. The secret key is the master key to the back office. The staff login is a personal badge with the right floors on it. The admin token is the building manager's key ring.

8Best-practice checklist for good training data

Brainbox can only be as good as what it reads. These habits make the biggest difference.

Content

  • Start with what customers ask most: FAQs, prices and plans, billing, how-to guides, policies (refunds, cancellations, opening hours).
  • One topic per document or per section, with clear headings. A chunk is about half a page: it should make sense on its own.
  • Write answers as full sentences. "Refunds: 5d" is hard to use; "Refunds are paid back within 5 working days" is easy.
  • Use the words your customers use ("bill" and "invoice", "meter" and "reading").
  • Prefer text PDFs and Word files. If you can't select the text in a PDF, it's a scan: Brainbox can't read it.
  • Remove outdated versions: delete the old source before uploading the new one.
  • Avoid huge raw exports (logs, number tables): they crowd out useful passages.

Audience and safety

  • Choose the audience every time. Leave internal procedures, prices you don't publish and anything personal as internal or admin.
  • Use public only for what you would publish on your website.
  • Strip passwords, bank details and personal data before uploading.
  • Support tickets: connect with a read-only helpdesk token, keep them internal unless you are sure, and map the ticket id so re-syncs stay clean.

Keep improving

  • Check the Knowledge gaps inbox weekly and answer the most-asked questions first.
  • Use "also resolve similar" to close duplicates in one go.
  • Look at the overview's answer rate and top questions every month.
  • After a big upload, ask Brainbox a few real questions as a customer would.
  • Re-sync support sources regularly (or automate the sync call).
  • Check failed sources: the reason is always shown.
The one-sentence rule

Give Brainbox the answers your best support agent would give, written down clearly, labelled with who may hear them, and keep the gap inbox empty.

Tenant resolution

  • The tenant (company) always comes from the credential: the key's tenant or the staff user's tenant.

CORS

Every origin, method and header is allowed, with allow_credentials=false: a page on any domain can call the API with its key in a header (keys are never cookies).

Timeouts and performance

  • Chat can take up to about 180 seconds when the AI model is busy (the server waits up to 180 s for the model). Set client timeouts to at least 200 s (sdk-web uses 200,000 ms), and make sure any reverse proxy in front of your own servers allows it too. Repeated questions are answered from the cache in milliseconds.
  • Training endpoints return 202 immediately; the work happens in the background. Poll GET /api/train/sources/{id} (or /api/ingest/status/{task_id}) every few seconds until status is completed or failed.
  • Support-system fetches time out after 30 s per request.

Versioning

The API is version 1.0.0 (reported by GET / and GET /api/health) and has no version prefix in the path. Changes are made additively: new optional request fields and new response fields can appear at any time, so clients must ignore fields they don't know. Fields marked "additive" below were added after the first release of an endpoint. Times are ISO-8601 strings in UTC (chat-session times may come without an offset: treat them as UTC). Ids of sources, sessions and tasks are UUID strings; ids of gaps, staff, notifications, keys and messages are integers.

11Quick-start recipes

Copy-paste examples for the common jobs, each in curl, JavaScript (fetch) and Python (requests). Training examples run on a server with a secret key; recipe 6 is the only one meant for a browser.

Setup used by every recipe

curl (bash)
export BB=https://port.smartpowerbilling.com
export SK=sk_live_xxx          # secret key: servers and scripts only
JavaScript (Node 18+, server side)
const BB = 'https://port.smartpowerbilling.com';
const SK = process.env.BRAINBOX_SECRET_KEY;          // sk_live_xxx, never ship it to a browser

async function bb(method, path, body, token = SK) {
  const isForm = body instanceof FormData;
  const res = await fetch(BB + path, {
    method,
    headers: { Authorization: `Bearer ${token}`, ...(body && !isForm ? { 'Content-Type': 'application/json' } : {}) },
    body: isForm ? body : body ? JSON.stringify(body) : undefined,
    signal: AbortSignal.timeout(200_000),               // chat can take ~180 s
  });
  const data = await res.json().catch(() => ({}));
  if (!res.ok) throw new Error(`${res.status} ${JSON.stringify(data.detail)}`);
  return data;
}
Python 3 (requests)
import os, time, requests

BB = "https://port.smartpowerbilling.com"
SK = os.environ["BRAINBOX_SECRET_KEY"]                 # sk_live_xxx

def bb(method, path, token=SK, **kw):
    r = requests.request(method, BB + path, headers={"Authorization": f"Bearer {token}"},
                         timeout=kw.pop("timeout", 200), **kw)
    if not r.ok:
        raise RuntimeError(f"{r.status_code} {r.text}")
    return r.json()

Run inside the brainBox folder (with Docker: docker exec -i brainbox-api python -m app.cli …). The CLI talks to the database directly and needs no token.

# API keys
python -m app.cli keys create --tenant acme --type publishable --name "Website widget"
python -m app.cli keys create --tenant acme --type secret --name "Odoo server" --expires 2027-12-31

python -m app.cli staff create --tenant acme --email owner@acme.com --role owner [--name "Ada"]

Deployment order (turning keys on safely)

  1. Deploy with REQUIRE_API_KEY=false. The new tables and columns are created on startup; existing clients keep working.Set JWT_SECRET_KEY, BRAINBOX_ADMIN_TOKEN, DASHBOARD_URL and SMTP_* now too.
  2. Register a key for every existing client. Websites that already ship a key: import that exact key as publishable (--key-stdin). Servers (Odoo, backends, admin tools): create a secret key and put it in that server's settings, never in front-end code.Check with python -m app.cli keys list.
  3. Decide LEGACY_DOC_AUDIENCE and relabel sensitive sources (Training page or PATCH /api/train/sources/{id}).
  4. Create each company's first owner (staff create or POST /api/admin/staff) so they can invite their team.
  5. Switch to REQUIRE_API_KEY=true and restart. Watch the logs for 401/403; switching back to false rolls back instantly.
Operational notes
  • Training runs inside the API process: a restart marks running jobs as failed ("Interrupted by a server restart"). Re-upload or re-sync them.
  • Login rate limiting is per worker process; with several workers, put a rate limit in your reverse proxy too.
  • Reverse proxies in front of brainBox must allow requests of at least 200 s for /api/chat and uploads of 25 MB for /api/train/file.
