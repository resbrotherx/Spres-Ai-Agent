2A company wants keys

Onboarding a company takes five minutes: pick a name for it, give it a first owner, and let that owner (or you) create its keys.

In plain words

Think of the server as the head office. Companies never get access to the head office itself: they get keys (for their websites and systems) and staff accounts (for their people). Each key and account belongs to exactly one company, called a tenant, and can only see that company's knowledge.

  1. Choose the tenant id. A short, lowercase name with no spaces, e.g. acme. Nothing needs to be "created": the tenant exists as soon as a key or staff account uses the name. Case-sensitive free text. A typo (Acme vs acme) silently makes a second, empty company, so write it down and copy-paste it. Check existing names with keys list / staff list.
  2. Create their first owner. One person at the company who will manage everything else. Either from the server CLI or over HTTPS with the admin token (commands below). Without a password you get an invite link valid for 7 days.
  3. Send the owner the invite link and the dashboard address. They set their password and log in to the staff dashboard (section 3).
  4. Keys: they create their own, or you do. In the dashboard: Settings → API keys (admins and owners). Publishable key for websites and apps, secret key for servers and Odoo. Or you create them with the CLI / admin API.
  5. Send the connection details (list below) and confirm the key works: curl -H "X-API-Key: sk_live_xxx" https://port.smartpowerbilling.com/api/health answers with the key's type and tenant.

Create the first owner

On the server (CLI inside the API container)
# invite link (valid 7 days) — send it to the person
docker exec brainbox-api python -m app.cli staff create --tenant acme --email owner@acme.com --role owner --name "Ada Lovelace"

# or set a password now (you are prompted twice, nothing is echoed)
docker exec -it brainbox-api python -m app.cli staff create --tenant acme --email owner@acme.com --role owner --password

docker exec brainbox-api python -m app.cli staff list --tenant acme
From anywhere, with the admin token (BRAINBOX_ADMIN_TOKEN from the server's .env)
curl -X POST https://port.smartpowerbilling.com/api/admin/staff \
  -H "X-Admin-Token: $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"tenant_id":"acme","email":"owner@acme.com","full_name":"Ada Lovelace","role":"owner"}'
# -> {"user": {...}, "invite_url": "https://.../#/accept-invite?token=..."}

Create keys yourself (optional)

# the raw key is printed ONCE — copy it into your password manager straight away
docker exec brainbox-api python -m app.cli keys create --tenant acme --type publishable --name "Acme website"
docker exec brainbox-api python -m app.cli keys create --tenant acme --type secret --name "Acme Odoo" --expires 2027-12-31
docker exec brainbox-api python -m app.cli keys list --tenant acme      # never shows raw keys

# same over HTTPS
curl -X POST https://port.smartpowerbilling.com/api/admin/keys \
  -H "X-Admin-Token: $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"tenant_id":"acme","key_type":"secret","name":"Acme Odoo"}'      # -> {..., "api_key": "sk_live_..."}

Send the company
  • Backend URL: https://port.smartpowerbilling.com
  • Their tenant id, e.g. acme
  • Dashboard link + the owner's invite link
  • Publishable key (websites, apps)
  • Secret key (Odoo, servers) — through a password manager share or another secure channel, not in a normal email or chat
  • Script tag: https://port.smartpowerbilling.com/sdk/brainbox-web-sdk.js
  • The Odoo add-on zip (if they use Odoo)

  • BRAINBOX_ADMIN_TOKEN (opens every company)
  • JWT_SECRET_KEY (lets anyone forge staff logins)
  • POSTGRES_PASSWORD or the .env file
  • The server's SSH password or keys
  • Another company's keys or tenant id
  • A secret key for use in a website or mobile app — give a publishable key instead

Revoking and rotating keys

A revoked key stops working on the next request. To rotate (replace a key without downtime): create the new key, let the company install it, check it works, then revoke the old one. Each key shows last used, so you can see when the old one went quiet.

docker exec brainbox-api python -m app.cli keys list --tenant acme     # find the id (ID column)
docker exec brainbox-api python -m app.cli keys revoke 42
curl -X DELETE https://port.smartpowerbilling.com/api/admin/keys/42 -H "X-Admin-Token: $ADMIN_TOKEN"

Company admins can do the same themselves in Settings → API keys (they only see their own tenant's keys). If a secret key leaks, revoke it first and ask questions later: the only effect is that their integration stops until the new key is installed.

3Staff and the dashboard

Staff are the people at a company who look after their assistant: they train it, read what users asked, answer the questions it couldn't, and manage keys and colleagues. They all use one web page: the staff dashboard.

What you need

  • An owner (or admin) account for the company — created by you as in section 2. Everyone else is invited from the dashboard by that person.
  • A hosted dashboard (below), and DASHBOARD_URL in the server's .env pointing to it, so links in invite and password-reset emails open the right page.
  • For emails (invites, alerts): the SMTP_* settings in .env. Without them, everything still works but the invite link must be copied and sent by hand (the dashboard shows it).

Where staff log in

The dashboard is the StaffDashboard component of the React SDK (spres-react). Today it runs from the sdk-react preview app on your machine:

cd ai\sdk-react\preview
npm install
npm run dev                         # then open http://localhost:4173/#/staff

That is fine for you, but companies need a real address. Two ways to host it:

A. Build the preview and serve it with nginx

Quickest. Build with the server URL and serve the static files, e.g. at https://port.smartpowerbilling.com/dashboard/:

# preview/.env.local:
VITE_BRAINBOX_API_URL=https://port.smartpowerbilling.com
npx vite build --base=/dashboard/
# nginx (same server block)
location /dashboard/ {
    alias /var/www/brainbox-dashboard/;
}

Copy preview/dist/ to /var/www/brainbox-dashboard/. Staff open …/dashboard/#/staff.

B. A small app of your own

Cleaner for customers (no chat demo pages). Any React app:

import { StaffDashboard } from 'spres-react';

export default function App() {
  return <StaffDashboard
    apiUrl="https://port.smart…"
    brandName="Brainbox" />;
}

Build it and host the files anywhere (nginx, Netlify…). Needs spres-react 1.1.0, which is not on npm yet (section 7) — until then build it from the repo.

Then set DASHBOARD_URL and restart the API:

# /var/www/Spres-Ai-Agent/brainBox/.env
# option A (the preview forwards #/accept-invite links to #/staff/...)
DASHBOARD_URL=https://port.smartpowerbilling.com/dashboard
docker restart brainbox-api
Never build a secret key into the dashboard

Anything in a VITE_… variable ends up inside the JavaScript files that every visitor downloads. The dashboard does not need a key: staff log in with email and password.

Inviting staff and roles

In the dashboard: Staff → Invite, enter email, name and role. The person receives an email (or the admin copies the link shown) and sets a password within 7 days. Roles, from most to least powerful:

RoleCan
ownerEverything, including managing admins and other owners. A company always keeps at least one active owner.
adminInvite / change / remove trainers and viewers, change settings, manage API keys.
trainerTrain the AI, answer / dismiss / reopen knowledge gaps.
viewerRead everything: overview, gaps, conversations, training sources, staff list, settings.

Endpoints behind the dashboard: POST /api/staff/login, POST /api/staff/invite (admin+), PATCH / DELETE /api/staff/{id}, POST /api/staff/{id}/resend-invite, POST /api/staff/accept-invite, /forgot-password, /reset-password, GET /api/staff. Details: Training & API reference section 6 "Staff roles" and section 10. One email address = one staff account in one company.

# server-side helpers when someone is locked out
docker exec -it brainbox-api python -m app.cli staff set-password owner@acme.com
docker exec brainbox-api python -m app.cli staff deactivate someone@acme.com   # immediate

Unanswered questions (knowledge gaps)

  1. The assistant can't answer. No matching knowledge, a low-confidence match, the model said it doesn't know, the model was unavailable, or a user gave a thumbs-down.
  2. It appears in the dashboard under Knowledge gaps, grouped by question with a counter of how often it was asked.
  3. Staff are notified. An in-app notification (bell) for each active staff member, and an email if SMTP is configured on the server, the staff member has email alerts on, and the company allows it (Settings → Alerts). Emails are capped per hour (EMAIL_MAX_PER_HOUR, default 20).
  4. A trainer answers it with Answer & train: the answer becomes a training source, the gap is marked resolved, and the next user gets the new answer. Full flow: Training & API reference, section 5. Email needs SMTP_HOST + SMTP_FROM (or SMTP_USER); also SMTP_PORT, SMTP_PASSWORD, SMTP_TLS = starttls / ssl / none.

4Training the AI

Training means giving a company's assistant its knowledge: files, pasted text, or a connection to another system (for example a support desk). Each company trains its own assistant; you rarely need to do it for them.

The one rule to remember: audiences

Every source has an audience (public, customer, vendor, internal, admin) that decides who may get answers from it. New sources default to internal. Website visitors (publishable keys) only ever see public knowledge, so a company that wants its website bot to answer from a document must mark that document public.

5Sharing the Odoo add-on

A company that uses Odoo 17 gets the assistant inside Odoo by installing one add-on, Brainbox AI (brainbox_ai, version 17.0.2.0.0). You send them a zip; they install it and paste in a secret key. They do not copy any chat code: the chat window is the web SDK, bundled inside the add-on.

What to send

  • docs/brainbox_ai-odoo17-v2.0.0.zip — the add-on folder (21 files, no caches). Or give them read access to a git repository containing only the brainbox_ai folder.
  • A secret key for their tenant (section 2) — the add-on does not work with a publishable key for logged-in users, because only a secret key lets Odoo say who each user is and what role they have.
  • The backend URL https://port.smartpowerbilling.com and their tenant id.

What the company does

  1. Unzip into an addons folder. The result must be <addons path>/brainbox_ai/__manifest__.py, in a folder listed in addons_path of their odoo.conf (Odoo.sh: commit the folder to their repository).
  2. Restart Odoo.
  3. Apps → Update Apps List (developer mode), search Brainbox AI, click Activate.
  4. Settings → Brainbox AI: fill in Backend URL, Tenant ID, Secret API key, click Test connection, choose a display mode, save.

The settings, briefly

SettingWhat it is
Backend URLhttps://port.smartpowerbilling.com (without /api).
Tenant IDTheir tenant id. Optional with a secret key (the key already says which tenant).
Secret API key (sk_...)Kept on the Odoo server, never sent to browsers, never shown again. Empty = keep the stored key; "Remove it on save" deletes it.
SDK script URLOptional: load the SDK from a URL (e.g. https://port.smartpowerbilling.com/sdk/brainbox-web-sdk.js) instead of the bundled copy.
Test connectionButton: the Odoo server calls /api/health with the stored key; it reports success, or a failure if the server cannot be reached or the key is rejected.
Display mode, PositionFloating launcher (default), docked sidebar, systray icon only, or disabled; bottom-right / bottom-left.
Allowed groupsWho gets the assistant. Empty = all internal users.
Role mapping, role groupsWhich role (internal, customer, vendor, public…) each kind of user gets; decides which knowledge they may read.
Colors, names, logo, welcome message, quick actionsAppearance of the chat.

Every setting in detail, display modes, embedding the chat in a form and the role precedence: Odoo guide, section 7 "Installation and configuration" and section 5 "Who sees what". Onboarding checklist for a company: Odoo guide, section 6.

Updating the chat (SDK) inside the add-on

The add-on ships a copy of sdk-web/brainbox-web-sdk.js in static/lib/brainbox-web-sdk/. When the web SDK changes, copy it in, upgrade the module, and send a new zip:

# in odoo\custom_addons\brainbox_ai (PowerShell)
.\tools\sync_sdk.ps1 -SdkPath C:\Users\USER\Documents\PERSONAL\ai\sdk-web
# -Version 2 (download from npm via jsDelivr) only works once spres-web is published (section 7)

A company can also skip updates by setting SDK script URL to your server's copy, which every deploy keeps current. Bump the version in __manifest__.py and the zip name when you change the add-on, so companies can tell versions apart.

# rebuild the zip, without Python caches (PowerShell or cmd, in odoo\custom_addons)
tar -a -cf brainbox_ai-odoo17-v2.0.1.zip --exclude=__pycache__ --exclude=*.pyc brainbox_ai

The local Odoo test instance

cd C:\Users\USER\Documents\PERSONAL\odoo
# run Odoo: http://localhost:8069, database test_odoo_db (the only one with brainbox_ai installed)
.venv\Scripts\python.exe odoo-bin -c odoo.conf
# upgrade the add-on after changing it (add --http-port 8075 if 8069 is busy)

6Deployments and backups

You never copy files to the server by hand. You push to the main branch on GitHub; GitHub checks the code and tells the server to update itself. The whole thing takes about a minute.

  • Watch it: GitHub → Actions tab → "Deploy brainBox". A red cross means look at the log of the failing step.
  • Re-run without a code change: Actions → Deploy brainBox → Run workflow.
  • Postgres, Redis and Ollama keep running during a deploy; only the API restarts (a few seconds of downtime). The API image is rebuilt only when requirements.txt or the Dockerfile changed.
  • Setup: GitHub secrets DEPLOY_HOST, DEPLOY_USER, DEPLOY_KNOWN_HOSTS, DEPLOY_SSH_KEY and the forced-command line in the server's authorized_keys — see deploy/README.md.

Manual deploy

# on the server
bash /var/www/Spres-Ai-Agent/deploy/deploy.sh                  # same as GitHub does
FORCE=1 bash /var/www/Spres-Ai-Agent/deploy/deploy.sh          # restart even if already up to date
FORCE_BUILD=1 bash /var/www/Spres-Ai-Agent/deploy/deploy.sh    # also rebuild the API image

deploy.sh only fast-forwards: if someone edited files directly on the server and committed there, it stops with an error instead of throwing their work away. Fix it by hand (git status, git log) before deploying again.

Database changes ("migrations")

There is no separate migrate command. Every time the API starts it runs init_db, which creates missing tables and adds missing columns (CREATE … IF NOT EXISTS, ADD COLUMN IF NOT EXISTS). It is safe to run any number of times and never deletes data. A deploy therefore upgrades the database automatically. Take a backup before a big release anyway.

Backups

Only the Postgres database matters: it holds every company's knowledge, chats, keys and staff. Redis is a cache and the AI model can be downloaded again. Also keep a copy of brainBox/.env in your password manager — without JWT_SECRET_KEY everyone is logged out, without the rest you start over.

# on the server — one compressed dump file
mkdir -p /root/backups
docker exec brainbox-postgres pg_dump -U spres -Fc spres_ai > /root/backups/brainbox-$(date +%F).dump

# copy it off the server (from your laptop)
scp root@165.227.77.33:/root/backups/brainbox-2026-10-09.dump .

# optional: nightly at 03:00, keep 14 days (crontab -e)
0 3 * * * docker exec brainbox-postgres pg_dump -U spres -Fc spres_ai > /root/backups/brainbox-$(date +\%F).dump && find /root/backups -name 'brainbox-*.dump' -mtime +14 -delete

Restore

Restoring replaces the whole database with the backup. Stop the API first so nothing writes in the meantime.

docker stop brainbox-api
docker exec brainbox-postgres dropdb -U spres spres_ai
docker exec brainbox-postgres createdb -U spres spres_ai
docker exec -i brainbox-postgres pg_restore -U spres -d spres_ai --no-owner < /root/backups/brainbox-2026-10-09.dump
docker start brainbox-api
curl -s http://127.0.0.1:8000/api/health

Test a restore on a spare server once, so you know the backups are good before you need them. After restoring an older backup the API adds any newer columns itself on start.

Publishing an npm package

  1. Bump the version in package.json. npm refuses to publish a version number twice, ever (even after unpublishing). npm version patch (1.1.0 → 1.1.1), minor for new features, major for breaking changes.
  2. Build and check. npm run build (sdk-react: TypeScript → dist/; sdk-web: minified file in dist/, run automatically by prepublishOnly).
  3. Log in once with the npm account that owns the packages: npm login (or an automation token in ~/.npmrc — never commit that file).
  4. Publish and commit the version bump.
cd ai\sdk-react
npm install
npm run build
# list exactly which files will be uploaded: no .env, no keys
npm pack --dry-run
npm publish --access public

cd ..\sdk-web
npm publish --access public   # prepublishOnly runs: node --check + build
# Python (sdk-python): bump version in pyproject.toml, then
pip install build twine
python -m build
twine upload dist/*          # uses a PyPI API token; see PUBLISHING_GUIDE.md

Step-by-step account and token setup for npm and PyPI: ai/PUBLISHING_GUIDE.md. After publishing spres-web, websites can also use https://cdn.jsdelivr.net/npm/spres-web@2, and the Odoo add-on's sync_sdk.ps1 -Version 2 starts working.

8Moving to a new server

Moving means: set up a fresh server with one script, copy the database across, point the domain at the new machine, and tell GitHub where to deploy. Plan about an hour, most of it waiting for downloads. Users notice only a short pause while DNS switches.

The current server is shared

165.227.77.33 also runs unrelated services. On it, only ever touch the brainbox-* containers, the brainBox nginx site and /var/www/Spres-Ai-Agent.

Step by step

  1. Create the new server. Ubuntu 22.04 or 24.04, at least 4 vCPU and 8 GB RAM for qwen2.5:1.5b on CPU (more cores = faster answers; a GPU server for answers under 5 s), 40 GB+ disk. Log in with an SSH key.
  2. Run the bootstrap script. It installs Docker, clones the repo, writes a new .env with fresh secrets, starts the containers, downloads the model and waits for health. 
    curl -fsSL https://raw.githubusercontent.com/resbrotherx/Spres-Ai-Agent/main/deploy/bootstrap-server.sh -o bootstrap-server.sh
sudo bash bootstrap-server.sh https://github.com/resbrotherx/Spres-Ai-Agent.git port.smartpowerbilling.com
  3. Carry over the secrets that must not change. Copy JWT_SECRET_KEY (keeps staff logged in), BRAINBOX_ADMIN_TOKEN, DASHBOARD_URL, SMTP_* and any tuning variables from the old .env into the new one. Keep the new POSTGRES_PASSWORD (the new database was created with it). Then docker restart brainbox-api. API keys and staff passwords live in the database, so they move with the backup — companies change nothing.
  4. Back up the old database and restore it on the new server (section 6). For a clean cut-over, take the final backup right before the DNS switch. 
    # old server
docker exec brainbox-postgres pg_dump -U spres -Fc spres_ai > /root/backups/move.dump
# copy across (from the old server, or via your laptop)
scp /root/backups/move.dump root@NEW_IP:/root/move.dump
# new server: the restore commands from section 6 (stop api, dropdb, createdb, pg_restore, start api)
  5. Test before switching. On the new server curl -s http://127.0.0.1:8000/api/health and curl -s -H "X-API-Key: sk_live_xxx" http://127.0.0.1:8000/api/health with a real key (shows its tenant), then ask one question.
  6. nginx and HTTPS. Create the nginx site printed by the script (proxy to 127.0.0.1:8000, location /sdk/, proxy_read_timeout 300s), plus location /dashboard/ if you host the dashboard (section 3).
  7. Switch DNS. Point the A record of port.smartpowerbilling.com to the new IP (lower the TTL to 300 a day before). Once it resolves to the new server, run certbot --nginx -d port.smartpowerbilling.com.
  8. Update GitHub. Secrets DEPLOY_HOST (new IP) and DEPLOY_KNOWN_HOSTS (ssh-keyscan -t ed25519 NEW_IP); add the forced-command deploy key line to the new server's ~/.ssh/authorized_keys (deploy/README.md). Then Actions → Run workflow to prove it works.
  9. Firewall, backups, clean-up. Section 9 checklist, the nightly backup cron (section 6). Keep the old server stopped (not deleted) for a week, then remove its brainbox containers and volumes.

The AI model is not in the backup: the bootstrap script downloads the one named in OLLAMA_MODEL (by hand: docker exec brainbox-ollama ollama pull <model>). Changing model = edit OLLAMA_MODEL, pull it, restart the API.

Performance settings (answer speed)

Answers are written by the AI model running on the server's CPU, so speed depends mostly on the number of CPU cores, the model size and how much text goes into each prompt.

What to expect today

Production runs qwen2.5:1.5b on the shared 4-core CPU with the values in the "Production" column below. Measured: about 9–20 s per answer, depending on server load and answer length. Tuning cannot make a CPU much faster than that. For answers under 5 s, use a hosted OpenAI-compatible API (LLM_PROVIDER=openai, e.g. Groq llama-3.1-8b-instant: about 1–3 s, paid per use, questions leave your server) or move Ollama to a GPU server.

These variables in brainBox/.env exist in the code as of this writing (restart the API after changing them):

VariableProductionEffect
OLLAMA_MODELqwen2.5:1.5bThe model. Smaller = faster, larger = better answers (llama3.2:3b is roughly twice as slow on the same CPU). Must be pulled into the ollama container. Same value in .env.example; code fallback if unset: llama2.
LLM_PROVIDERollama (default)openai = use any OpenAI-compatible API instead of the local model (much faster, costs money per question, questions leave your server). The other provider is tried as a fallback when configured.

The API logs one line per answer: Ollama answered in 9.3s (load 0.0s, prompt 812 tok, answer 140 tok). A large load means the model was reloaded; a large prompt means lower the RAG settings. docker stats shows whether the CPU is saturated.

9Security checklist

Go through this list after every server change, and once a quarter anyway.

Network

  • Only ports 22, 80 and 443 are open to the internet. ufw allow 22/tcp, 80/tcp, 443/tcp, default deny incoming — and/or the same rules in the cloud provider's firewall (DigitalOcean → Networking → Firewalls).
  • Port 8000 is not reachable from outside. Docker publishes container ports past ufw, and docker-compose.yml maps the API as 8000:8000 on all interfaces. Block 8000 in the cloud firewall, or change the mapping to "127.0.0.1:8000:8000" (nginx reaches it locally either way). Test from your laptop: curl -m 5 http://165.227.77.33:8000/api/health must time out.
  • Postgres, Redis and Ollama are never published. Postgres is bound to 127.0.0.1:5432 (use an SSH tunnel to inspect it); Redis and Ollama have no ports: at all. Keep it that way: Redis and Ollama have no password.
  • HTTPS only. certbot installed with automatic renewal (certbot renew --dry-run succeeds).

Access

  • SSH keys, not passwords. In /etc/ssh/sshd_config: PasswordAuthentication no (and ideally PermitRootLogin prohibit-password), then systemctl reload ssh — only after confirming your key login works in a second terminal.
  • The GitHub deploy key is restricted to command="bash /var/www/Spres-Ai-Agent/deploy/deploy.sh" with restrict, and is used for nothing else.
  • No server password is written down in the repo, in documents or in chats. Secrets live only in the server's .env and your password manager.
  • The repository is public: never commit .env, keys, dumps or .npmrc tokens. Before every commit, git status and look.

Secrets and keys

  • Secret keys (sk_) only on servers (Odoo, back-ends, scripts). Websites and mobile apps get publishable keys (pk_) or go through a server proxy.
  • BRAINBOX_ADMIN_TOKEN and JWT_SECRET_KEY are long random values (the bootstrap script generates 64 hex characters) and the startup log shows no placeholder warning.
  • Rotate the admin token if it may have been seen (change .env, restart the API). Changing JWT_SECRET_KEY logs out every staff member — do it if a staff session may have been stolen.
  • REQUIRE_API_KEY=true (the default). false is a migration-only kill switch that turns off key checks for everyone.
  • DEBUG=false in production.
  • Unused keys revoked: keys list shows last used; revoke keys of companies that left and keys that have not been used for months. Deactivate staff who left.
  • Backups exist off the server, and a restore has been tested (section 6). Backups contain every company's data: store them encrypted.

10Troubleshooting

Start with the three health checks, then the logs. Almost every problem shows up in docker logs brainbox-api.

First look

# from anywhere: through nginx + HTTPS
curl -s https://port.smartpowerbilling.com/api/health
# on the server: straight to the API (skips nginx)
curl -s http://127.0.0.1:8000/api/health
# is a key valid, and for which tenant?
curl -s -H "X-API-Key: sk_live_xxx" https://port.smartpowerbilling.com/api/health
# database, cache and vector checks (secret key)
curl -s -H "X-API-Key: sk_live_xxx" https://port.smartpowerbilling.com/api/health/db

# on the server

docker logs --tail 50 brainbox-ollama
docker stats --no-stream                    # CPU / memory per container
df -h /                                     # disk full breaks everything

If 127.0.0.1:8000 works but the public URL does not, the problem is nginx or DNS (nginx -t, systemctl status nginx, /var/log/nginx/error.log). A 502 from nginx means the API container is down; a 504 means it answered too slowly.
